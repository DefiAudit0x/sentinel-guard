# Security

## Scope

Sentinel Guard is a local prototype that evaluates an action/resource pair against in-memory policy rules and evaluates a caller-supplied, already-decoded transaction dictionary. For simulator calls, a supplied resource must exactly match a valid transaction recipient; when resource is omitted, the recipient is used for policy evaluation. Policy matching is exact: a rule without a resource applies to any resource for its action; a resource-specific rule must match exactly. Any matching `DENY` overrides matching `ALLOW` rules, regardless of rule order. When no rule matches, policy evaluation returns `default_deny`.

The simulator only combines these local decisions. It does not read blockchain or network state, sign or submit transactions, execute them, or request human approval. It is not a production security boundary.

## Trust boundaries and inputs

The caller supplies the action, resource, transaction fields, in-memory policy rules, and descriptive signals such as `recipient_is_contract`, `recipient_code_changed`, `previous_interactions`, and `account_age_days`. The simulator checks that an explicit resource agrees with a valid transaction recipient, but it does not independently establish that the supplied values describe a real transaction or account, nor does it parse or authenticate raw transaction data.

`known_malicious` is a caller-provided Boolean signal, not a verified finding. After the analyzer's input checks, `true` produces `BLOCK` with score 100; when omitted, it defaults to `false` for this signal only. Sentinel Guard does not fetch or verify a malicious-address list, so this result alone does not establish that a recipient is malicious.

The analyzer rejects missing or invalid recipients, non-integer, Boolean, or negative amounts, invalid interaction counts or account ages, and non-Boolean values for the three Boolean signals. Its amount threshold and score rules are experimental heuristics, not established security standards or a trusted reputation service.

## Failure behavior

The simulator validates the request wrapper before calling either evaluator. An invalid wrapper produces `BLOCK` with `INVALID_INPUT`, and neither evaluator is run. For a valid wrapper, policy and risk evaluation are attempted independently. An evaluator exception or an invalid result contract is recorded as an error and makes the overall decision `BLOCK`; the other evaluator is still attempted. A policy denial or risk `BLOCK` also makes the final decision `BLOCK`. A risk `WARN` remains `WARN` when policy allows and is never converted to `ALLOW`.

These are implemented behaviors. The repository tests exercise policy deny-overrides and default-deny cases, selected risk inputs and thresholds, wrapper validation, evaluator failures, and decision combination. Passing tests establishes only those tested behaviors for the local implementation and fixtures; it does not establish production security or safety for real transactions.

## Current limitations

The core simulator has no policy loader or persistence: callers supply its in-memory policy rules. Separately, the bounded JSON adapter loads an explicitly selected local policy file and fails closed on loading errors; it does not persist or modify that file. The core simulator, JSON adapter, and generic preflight have no transaction-signing or submission path. A separate optional browser demonstration can request one fixed Testnet self-transfer after a local `ALLOW`, a two-minute exact review, and a second user click; the connected wallet must still confirm it. This is not a control on other applications or an enforcement boundary. The local UI loads the third-party Meteor executor when the user connects, so the application cannot guarantee that executor's behavior. There is no transaction parser, trusted on-chain or reputation data source, or production enforcement. Authentication, authorization, deployment hardening, and a production threat model are also outside this prototype's implementation. Do not treat a local `ALLOW` or the current tests as evidence that a real transaction is safe.

The local UI constructs a manifest containing only `meteor-wallet` and pins its executor URL to immutable Git commit `6369ad789d2f3aaf8e6ccb065021723111027174`. The installed `@hot-labs/near-connect` 0.12.0 also accepts injected-wallet events independently of that manifest, and an injected provider can replace a registered wallet with the same ID. Before constructing the connector, the UI registers capture-phase handlers that block both `near-wallet-injected` CustomEvents and matching parent-frame messages; after direct `connect({ walletId: "meteor-wallet" })`, it accepts only a returned wallet whose manifest is the exact locally pinned object. Connection remains click-initiated with `autoConnect: false`. Tests exercise both injection paths and reject a same-ID provider with a cloned manifest.

The UI's `connect-src` allows only the exact `raw.githubusercontent.com` origin needed for the pinned executor and `rpc.testnet.near.org`; `img-src` additionally permits that same GitHub origin for the Meteor icon. CSP is origin-based, so it cannot itself pin a GitHub path; the code contains the immutable executor URL, while the icon URL points to the repository's mutable `main` branch and is image-only. The manifest grants the executor NEAR Connect storage access, the `meteorCom` and `meteorComV2` external bridges, and permission to open only `https://wallet.meteorwallet.app` and `https://meteorwallet.app`. The UI requests account sign-in and includes a narrowly scoped `signAndSendTransaction` call for the fixed self-transfer, gated by local review and a separate click; that gate does not constrain the third-party executor. The executor is third-party code, is not audited here, and may behave beyond what the application source demonstrates; we cannot guarantee its behavior when the user connects. These controls do not independently audit or constrain that code, protect against arbitrary same-origin script compromise, or prove that the wallet is safe to use. The UI presents this risk before Connect and again before the optional transfer review.
